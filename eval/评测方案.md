# Memory Agent 端到端评测方案

> 目标：评测 Memory 2.2 的 **memory agent（记忆提取器）** 在真实多轮对话上的端到端价值——
> 即「把长对话交给 memory agent 提纯成记忆、存入 Qdrant、再按问题召回并回答」是否比
> 「不过 memory agent、直接把对话原文当记忆」更能答对 LongMemEval 的问题。
>
> 评测对象：`backend/memory/v22/`（extractor + memory_store + render）+ `backend/agents/memory_agent.py`
> 评测数据：复用 `eval/longmemeval/data/`（LongMemEval oracle / s_cleaned）
> 评测位置：`eval/`（已从 backend 提出，独立顶层文件夹）
> 文档日期：2026-08-17

---

## 1. 为什么是端到端，而不是单独评提取

memory agent 的产物是「记忆条目」，但记忆条目没有现成 gold 标注——LongMemEval 标注的是
**问题→答案**，不是「这段对话该提取成哪几条记忆」。所以纯提取质量只能靠人工小样本评
（见 §7 的辅助评测），难以规模化。

端到端把**提取质量间接可测化**：如果 memory agent 提取得好，那么用它提取出的记忆去召回+回答，
端到端准确率应当 ≥ 直接用对话原文召回+回答的准确率；如果它提取丢了关键事实或加了噪声，
端到端准确率会掉。这样就能在 LongMemEval 现成的 500 题+judge 上规模化度量 memory agent 的价值。

## 2. 评测对象与对照

| 组别 | 提取方式 | 存储 | 召回 | 说明 |
|------|----------|------|------|------|
| **A（实验组）** | memory agent 提取（v22 extractor） | Qdrant（dense+bm25 RRF） | `MemoryStore.search` | 完整 v22 链路，要评的对象 |
| **B（对照组·原文）** | 不提取，每轮对话原文直接当一条 memory 写入 Qdrant | Qdrant（dense+bm25 RRF） | `MemoryStore.search` | 同样走 Qdrant 检索，但跳过提取——隔离「提取」这一变量的贡献 |
| **C（对照组·旧链路）** | 不提取，原文当 memory 灌入 2.1 SQLite | 2.1 SQLite（关键词检索） | `MemoryAPI.search` | 即现有 `eval/longmemeval/run.py` 的结果，作为基线，复用已有 outputs |

> A vs B：固定存储与检索，只换「提取 vs 不提取」→ 量化 memory agent 提取的**净贡献**。
> A vs C：换掉整条链路（提取+向量检索 vs 原文+关键词检索）→ 量化 v22 相对旧链路的整体提升。
> B vs C：固定「不提取」，只换存储/检索（Qdrant RRF vs SQLite 关键词）→ 量化检索后端的差异，用于解释 A vs C 里多少来自检索、多少来自提取。

三组共用同一份 LongMemEval 数据、同一个 answer 模型、同一个 judge 模型，确保差异只来自被控变量。

## 4. 端到端流程（每题）

```
for each question q:
  1. 清空 Qdrant memories collection（或换一个 per-question collection）——干净 slate
  2. 摄入 haystack：
       A 组：把每个 haystack session 喂给 v22 extractor.extract()，
             由 memory agent 提纯成记忆 → 写入 Qdrant
       B 组：把每个 haystack turn 原文作为一条 Memory（domain=user/project）
             直接 store.upsert()，不过 memory agent
  3. 召回：hits = store.search(q.question, domains=[user,project,agent], top_k=K)
  4. 回答：把 hits 渲染成 [Recalled memories] 注入 system prompt，
             调 answer 模型（GLM-4.7-Flash，OpenAI 兼容端点）回答
  5. 写 {question_id, hypothesis, n_memories, n_extracted, n_dedup} 到 hyp.jsonl
然后 judge 批次：用 LongMemEval 官方 prompt 模板（eval/longmemeval/judge.py 已有）
             让 judge 模型对 hypothesis 打 yes/no
最后 metrics 汇总：overall / 按 question_type / task-averaged / abstention
```

### 4.1 A 组的「喂给 extractor」具体做法

extractor.extract() 需要一个 `ExtractionContext`，并会去 `HistoryStore.list_messages`
拉「最近对话」。评测里两种可行喂法：

- **(a) 逐 session 喂**：把每个 haystack session 当一次「agent 调用完成」事件——
  `user_text` = 该 session 最后一个 user turn，`final_text` = 最后一个 assistant turn，
  `channel_id`/`thread_id` 固定为本题的，先把整个 session 的 turn 写进 `session_messages`
  表（HistoryStore），再 extract。这样 extractor 拉到的「最近对话」就是该 session 的真实上下文。
- **(b) 逐 turn-pair 喂**：每个 (user, assistant) turn 对一次 extract，粒度更细、调用更多。

**采用 (a)**：与真实运行时「一次 agent 调用结束触发一次提取」语义一致，且调用次数可控
（~40 次/题 for s_cleaned）。turn-pair 粒度太细，memory agent 调用成本爆炸且不符合真实触发时机。

### 4.2 B 组的原文直写

为公平，B 组写 Qdrant 时也用 `Memory.create(text=f"[{role}] {content}", domain=...)`，
让 dense/bm25 在「原文」上跑——这样 A vs B 的差异纯粹是「提纯 vs 不提纯」，不是「向量化 vs 没向量化」。

## 5. 指标

### 5.1 主指标（端到端 QA 准确率，三组同口径）

- Overall accuracy
- Task-averaged accuracy
- 按 `question_type` 分组准确率（single-session-user / single-session-assistant / multi-session / temporal-reasoning / knowledge-update / single-session-preference）
- Abstention accuracy（`_abs` 题）

> judge 用 GLM-4.7-Flash（非官方，已在 judge log 里标注，不与 LongMemEval 论文 GPT-4o 数字直接比）。
> 三组之间同 judge 同口径，**组间可比**。

### 5.2 过程指标（诊断用，A 组额外记录）

| 指标 | 定义 | 作用 |
|------|------|------|
| 提取压缩比 | n_extracted_memories / n_haystack_turns | memory agent 把对话压缩了几成 |
| 提取丢弃率 | n_dropped / n_emitted | memory agent 判「不值得记」的比例 |
| 去重命中数 | n_skipped_dup | 同题内重复记忆被合并的次数 |
| 平均召回延迟 | p50/p95 of store.search | Qdrant 双路 RRF 的检索成本 |
| 平均提取延迟 | p50/p95 of extractor.extract | memory agent（Claude CLI 子进程）的提取成本 |
| 检索 recall@k | gold 证据 session 的记忆是否进 top-k | 见 §6 |

### 5.3 核心对照结论模板

- **提取净贡献** = acc(A) − acc(B)
- **v22 整体提升** = acc(A) − acc(C)
- **检索后端差异** = acc(B) − acc(C)

正值的提取净贡献 = memory agent 提取确实帮了端到端；若接近 0 或负，说明提取在丢信息或加噪声，需回到 §7 小样本诊断。

## 6. 检索 recall@k（可选辅助）

LongMemEval 每题带 `evidence_session_ids`。A 组写入 Qdrant 的每条 memory 记了 `source session id`（放进 payload 或 tags），
对问题做 `store.search` 后，看 top-k 命中的 memory 里有多少来自 evidence session：

```
recall@k = |top-k 命中里属于 evidence session 的 memory| / |evidence session 应有的 memory|
```

这能在「答错」时定位是**召回没捞到**（recall@k 低）还是**召回了但答错了**（recall@k 高但 QA 错）。
B/C 组同理。本指标可选，第一轮跑通可不做。

## 7. 提取质量小样本人工评测（辅助、必做）

端到端只能间接判提取好坏。为直接度量提取质量，自建 **20–30 条小样本**：

- 每条 = 一段构造的工作上下文（含：1 个该记的项目决策、1 个该记的用户偏好、1 个一次性指令、1 段过程性叙述、1 个未确认的猜测）
- gold = 该上下文应提取出的记忆条目（text + attributed_to + domain）+ 应被拒记的条目

对每条跑 `extractor.extract()`，人工/规则比对：

| 指标 | 定义 |
|------|------|
| 提取 precision | 提取出的记忆里「该记的」占比 |
| 提取 recall | gold 该记的记忆里被提取出的占比 |
| 拒记准确率 | 该拒记的（一次性指令/过程叙述/未确认猜测）是否真的没进记忆 |
| 归属准确率 | attributed_to（user/assistant）判对率 |
| domain 准确率 | 系统推导的 domain 判对率 |
| 关联真实性 | linked_memory_ids 全部在 offered_uuids 里（无幻觉 UUID） |

样本放 `eval/memory_agent/gold_samples.jsonl`，评测脚本 `eval/memory_agent/extract_eval.py`。
这一块规模小、可解释，是端到端之外对 memory agent 本身的直接质量度量。

## 9. 成本与节奏

- A 组每题 ~47 次 memory agent 调用。**执行后端已从 Claude CLI 子进程改为直接调 glm-5.2 API**（`ApiMemoryAgent`，`CT_MEMORY_AGENT_BACKEND=api`），省掉子进程启动开销、消除 asyncio subprocess pipe race，并发可安全提回 8。
- **并发提取**：`run_e2e.py` 的 `ingest_via_extractor` 用 `asyncio.Semaphore(concurrency=8)` 让一题内的多个 session 并发提取。API 后端下并发 8 稳定（5 题 smoke 验证），每题 ~260s，全量 A 组约 **~36 小时**（s_cleaned 每题 ~500 轮、提取 ~160 条，比 oracle 重）。
- **断点续跑**：`--resume` 读取已有 hyp.jsonl，跳过已做题，追加写入；中断后重跑同一命令即可续上，不丢已做题。
- **提取只做一次**：A2（全量喂 reader）与 A8（top_k 召回）的提取环节完全相同，`ingest_via_extractor` 返回 `(stats, extracted_mems)`，A2 直接用缓存的 `extracted_mems` 喂 reader、A8 走 Qdrant 召回——同一题的提取只跑一遍，两组共用。
- judge/answer 走 glm-5.2 代理（`http://10.0.0.10:13001`，OpenAI 兼容端点），已加 8 次 backoff。
- Qdrant 本地单机，无并发压力。

### 9.1 Token 用量统计

memory 系统端到端 token 消耗分三处，全部在 `run_e2e` 层用 `TokenCounters` 统一管理（不进 ExtractionResult）：

| 统计量 | 消耗点 | 记什么 | 怎么拿 |
|--------|--------|--------|--------|
| **#1 提取** | ApiMemoryAgent 调 glm-5.2 | prompt/completion/total tokens | 非流式响应 `usage` 字段，经 `extractor._last_usage` 透传 |
| **#2 回答** | `stream_openai_with_usage` 调 glm-5.2（answer 模型） | prompt/completion/total tokens | 流式 + `stream_options.include_usage`，最后 chunk 的 `usage` |
| **#4+#5 embedding** | 本地 BGE embedder（upsert 的 memory.text + search 的 query） | 等价 token 量（BGE 自己 tokenizer + 统一 tokenizer cl100k_base 双口径） | `MemoryStore.token_stats`，run_e2e 每题读后清零 |

每题 rec（hyp.jsonl）记录全部 token 字段；`extraction_stats.json` 汇总总 token、每题平均、每条记忆的提取 token 成本（extract_total/n_extracted）。

> embedding 是本地 BGE，不花 API token，记的是"等价 token 量"——用 BGE 自己的 tokenizer（最贴合 embedder 实际处理量）+ 统一 tokenizer cl100k_base（跨模型可比）双口径折算 embedder 处理的文本量。

### 9.2 memory agent 执行后端

`backend/agents/memory_agent.py` 的 `register_memory_agent()` 按 `CT_MEMORY_AGENT_BACKEND` 选：
- `api`（默认）：`ApiMemoryAgent`，直接 httpx 非流式调 `{CT_MEMORY_AGENT_BASE_URL}/chat/completions`，读 `usage` 经 `done` 事件透传。无子进程、无 asyncio race、并发安全。
- `cli`（回退）：`ClaudeCodeAgent`，原 Claude CLI 子进程后端。

配置（`backend/config.py`，`CT_MEMORY_AGENT_*` 前缀）：
```
CT_MEMORY_AGENT_BACKEND=api
CT_MEMORY_AGENT_MODEL=glm-5.2
CT_MEMORY_AGENT_BASE_URL=http://10.0.0.10:13001/v1
CT_MEMORY_AGENT_API_KEY=<glm key，默认回退 OPENAI_API_KEY>
CT_MEMORY_AGENT_MAX_TOKENS=4096
CT_MEMORY_AGENT_TEMPERATURE=0.0
```

## 9.5 s_cleaned 全量三方向测评（本次主跑）

> 本节是实际执行的测评过程，基于 oracle smoke 的迭代结论（见 §12）设计。

### 9.5.1 背景：oracle smoke 的迭代结论

在 oracle 前 25 题上做了多轮迭代，得到两个关键结论，决定了 s_cleaned 全量的设计：

1. **喂法是主因，prompt 是次要**：同 prompt 下旧喂法（只取末两轮）0.00、新喂法（全 session 转录）0.32；同喂法下 v1 通用 prompt 0.28、v2 事实单元 prompt 0.32，prompt 间差异远小于喂法间差异。
2. **v2 事实单元 prompt + 新喂法** 是 oracle 上的最佳组合（0.32），故 s_cleaned 全量采用此组合。

oracle 五方对比（temporal-reasoning 25 题）：

| 配置 | 提取/题 | 召回/题 | 0提取 | 准确率 |
|------|---------|---------|-------|--------|
| OLD工程+旧喂法 | 0.52 | 0.52 | 18/25 | 0.00 |
| v1通用+旧喂法 | 4.52 | 4.20 | 1/25 | 0.04 |
| v2事实单元+旧喂法 | 3.32 | 3.32 | 3/25 | 0.00 |
| v2事实单元+新喂法 | 7.68 | 6.08 | 2/25 | 0.32 |
| v1通用+新喂法 | 8.36 | 5.92 | 4/25 | 0.28 |
| B原文+top_k=8 | 27.68 | 8.0 | — | 0.92 |

### 9.5.2 三方向设计

s_cleaned 全量 500 题，三方向同 prompt（v2 事实单元）、同喂法（新喂法）、同 answer/judge 模型（glm-5.2），只差召回方式：

| 方向 | 提取 | 喂给 Reader 的记忆 | 代码 | 目的 |
|------|------|---------------------|------|------|
| **B** | 原文直写（不提取） | Qdrant top_k=8 召回 | `--group B --top-k 8` | 基线：不提取+召回截断 |
| **A2** | memory agent 提取 | **全部记忆，不截断** | `--group A --recall-mode all` | 提取+无召回截断：看提取后全量记忆能否答对 |
| **A8** | memory agent 提取 | Qdrant top_k=8 召回 | `--group A --recall-mode topk --top-k 8` | 提取+召回截断：看召回是否丢关键条 |

对照逻辑：
- **A2 vs B**：固定"喂给 reader 的记忆量"（A2 全量提取记忆 vs B 全量原文），但 A2 是提取后的、B 是原文——量化提取的净贡献（在无召回截断的公平条件下）。
- **A2 vs A8**：固定提取，只差召回方式（全量 vs top_k=8）——量化召回截断丢了多少。
- **A8 vs B**：固定 top_k=8 召回，只差提取 vs 原文——在有召回截断下提取的净贡献。

### 9.5.3 工程优化（让全量可行）

s_cleaned 每题 ~47 session、~493 轮，是 oracle 的 ~15-40 倍。三个优化让全量从 ~130 小时压到 ~10 小时：

1. **并发提取**（`--concurrency 8`）：一题内多个 session 并发提取，memory agent 是 Claude CLI 子进程（IO 密集），8 并发把每题墙钟压 ~8 倍。
2. **断点续跑**（`--resume`）：读已有 hyp.jsonl 跳过已做题，追加写入。中断（限流/断网/手动停）后重跑同一命令即续上，不丢已做题、不重复跑。
3. **提取只做一次**：A2 和 A8 的提取完全相同，`ingest_via_extractor` 返回 `(stats, extracted_mems)`，A2 用缓存的 `extracted_mems` 喂 reader、A8 走 Qdrant 召回——同一题提取只跑一遍。但当前实现里 A2 和 A8 是两次独立进程，提取会各跑一次；要真正只提取一次，需在同一进程内先跑 A2 再跑 A8 复用缓存，或把提取结果落盘。**本次采用分进程跑、各自提取**（实现简单、断点续跑更稳），代价是 A2/A8 各提取一遍。

> A2 和 A8 都写 `longmemeval_s_cleaned.A.hyp.jsonl`，会互相覆盖。实际跑时 A2 用 `--group A` + `--recall-mode all`，A8 用 `--group A` + `--recall-mode topk`——两者输出文件名相同。**需手动重命名**：A2 跑完改名为 `.A2.hyp.jsonl`，再跑 A8。或后续给 run_e2e 加 `--tag` 参数区分输出文件名。

## 12. oracle smoke 迭代记录（已完成）

在 s_cleaned 全量前，先在 oracle 前 25 题（全 temporal-reasoning）上做了多轮迭代，定位主因、调 prompt、调喂法。记录如下，作为 s_cleaned 全量设计的依据。

### 12.1 三组基线（旧工程 prompt + 旧喂法）

| 组 | 提取 | 检索 | 准确率 |
|----|------|------|--------|
| A（提取） | memory agent（旧工程 prompt） | Qdrant RRF | 0.00 |
| B（原文） | 不提取 | Qdrant RRF | 0.92 |
| C（旧链路） | 不提取 | SQLite 关键词 | 0.00 |

结论：A 全错、B 0.92、C 0.00。A vs B（固定检索只换提取）= 提取净负贡献；B vs C = Qdrant 向量检索远胜 SQLite 关键词。初步怀疑 memory agent 提取丢信息。

### 12.2 prompt 迭代（旧喂法，只改 prompt）

| prompt | 提取/题 | 0提取 | 准确率 |
|--------|---------|-------|--------|
| 旧工程（项目决策/技术选型） | 0.52 | 18/25 | 0.00 |
| v1 通用（事件/偏好/关系/时间） | 4.52 | 1/25 | 0.04 |
| v2 事实单元（最小语义事实单元） | 3.32 | 3/25 | 0.00 |

结论：三轮 prompt 调整，准确率始终在 0 附近。光改 prompt 撞天花板——主因不在 prompt 措辞。

### 12.3 喂法迭代（v2 prompt，只改喂法）

| 喂法 | 提取/题 | 召回/题 | 0提取 | 准确率 |
|------|---------|---------|-------|--------|
| 旧喂法（只取末两轮） | 3.32 | 3.32 | 3/25 | 0.00 |
| 新喂法（全 session 转录） | 7.68 | 6.08 | 2/25 | 0.32 |

结论：同 prompt 下换喂法，0.00 → 0.32。**喂法是主因**——旧喂法只取末两轮，漏掉前几轮的事实；新喂法把全 session 喂给 memory agent，漏提取大幅缓解。

### 12.4 prompt × 喂法交叉（新喂法下两 prompt 对比）

| prompt | 提取/题 | 召回/题 | 0提取 | 准确率 |
|--------|---------|---------|-------|--------|
| v2 事实单元 + 新喂法 | 7.68 | 6.08 | 2/25 | 0.32 |
| v1 通用 + 新喂法 | 8.36 | 5.92 | 4/25 | 0.28 |

结论：新喂法下两 prompt 基本持平（0.32 vs 0.28），但答对的题几乎不重合（只共同答对 2 题）——两 prompt 各有擅长的题，互补性强。s_cleaned 全量采用 v2 事实单元 + 新喂法（oracle 上略优）。

### 12.5 smoke 阶段总结论

1. **喂法是主因**：喂法改动带来的提升（+0.24~0.32）远大于 prompt 间差异（~0.04）。
2. **prompt 是次要**：在喂法修好后，两 prompt 都能上 0.28-0.32。
3. **检索后端有效**：B（Qdrant）0.92 vs C（SQLite 关键词）0.00，v22 的向量检索是正面贡献。
4. **天花板在 B 的 0.92**：A 现在 0.32，差距 0.60，可能来自漏提取、召回截断、时序合并不稳定——s_cleaned 全量的 A2（全量喂 reader）能验证"召回截断"这一项。
